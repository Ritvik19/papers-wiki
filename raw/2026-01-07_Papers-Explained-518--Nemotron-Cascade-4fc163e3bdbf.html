Papers Explained 518: Nemotron Cascade

This work proposes cascaded domain-wise reinforcement learning (Cascade RL) to develop general-purpose reasoning models, Nemotron-Cascade, capable of operating in both instruct and deep thinking modes. Departing from conventional approaches that blend heterogeneous prompts from different domains, Cascade RL orchestrates sequential, domain-wise RL, reducing engineering complexity and delivering state-of-the-art performance across a wide range of benchmarks.

The models and data are available at HuggingFace.

Supervised Fine Tuning

The SFT curriculum is a two-stage process trained for one epoch each:

Stage 1 (16K):

  • Focuses on general knowledge, math, science, and code reasoning.
  • Uses a maximum sequence length of 16K tokens.
  • General-domain data includes prompts with both “thinking” and “non-thinking” responses, while math, science, and code data only have “thinking” responses.

Stage 2 (32K):

  • Builds upon Stage 1 by incorporating longer responses (up to 32K tokens).
  • Adds tool use and software engineering skills.
  • Combines general-domain data with new math, science, code reasoning data (up to 32K tokens), and tool use/software engineering datasets.
  • Only general-domain data includes both “thinking” and “non-thinking” responses; other domains use only “thinking” responses.

The standard ChatML template is adopted and two control flags are introduced in the user prompt, /think and /no_think, which explicitly instruct the model to generate responses in the corresponding mode. This design supports both global and local control: appending the same flag to every user turn enforces consistent global behavior, while varying the flags across multi-turns enables dynamic switching within a single conversation. For tool calling tasks, all available tools in the system are specified in the system prompt within the <tools> and </tools> tags. The model is instructed to perform tool calls enclosed within the <tool_call> and </tool_call> tags.

Dataset

General-Domain Data

A massive corpus of 2.8 million samples containing 3.2 billion tokens is assembled from diverse general-domain datasets. These datasets cover a wide range of tasks, including dialogue, question answering, creative writing, safety, instruction following, role-playing, and more. For knowledge-intensive tasks, an additional 1.2 million samples (1.5 billion tokens) are collected from public datasets and domain-specific sources like law and ethics.

To ensure stylistic and qualitative consistency, parallel responses are generated for each prompt using two different language models: DeepSeek-R1–0528 (for thinking-based responses) and DeepSeek-V3–0324 (for non-thinking responses).

High-quality annotations are retained to preserve diversity. For prompts with verifiable answers, responses deviating from the ground truth are discarded. An auxiliary model (Qwen2.5–32B-Instruct) is used to cross-validate responses lacking ground truth, filtering out potentially low-quality generations.

Multiple responses are generated for each prompt using different random seeds to address data scarcity in domains like instruction following and creative writing. Multi-turn conversations are created by manually augmenting single-turn samples, either by adding a second turn for rewriting or by randomly concatenating samples

Math Reasoning Data

Stage-1:

  • Prompts are drawn from AceReason-Nemotron-1.1 which encompass prompts from AceMath, NuminaMath, and OpenMathReasoning datasets
  • Responses are generated by DeepSeek-R1
  • Maximum context length set to 16,384 tokens (16K) to prevent response truncation.
  • Data decontamination by removing samples overlapping with test sets from standard math benchmarks.
  • 353K unique prompts with an average of 7.8 responses per prompt.

Stage-2:

  • Prompts are derived from Stage-1 by filtering out easier questions (DeepSeek-R1 responses < 2K tokens).
  • Responses are generated by DeepSeek-R1–0528, which produces longer and more detailed reasoning trajectories compared to DeepSeek-R1.
  • Maximum context length set to 32,768 tokens (32K) to accommodate longer reasoning.
  • 163K prompts with an average of 11.5 responses per prompt.

Code Reasoning Data

Stage-1:

  • Prompts are sourced fromAceReason-Nemotron-1.1, including data from TACO, APPs, OpenCoder-Stage-2, and OpenCodeReasoning.
  • 172K unique prompts are obtained after removing duplicates.
  • DeepSeek-R1 generates 1.42M samples with an average of 8.3 responses per prompt and a maximum context length of 16,384 tokens (16K).
  • Samples with 9-gram overlap with test samples from coding benchmarks are filtered out.

Stage-2:

  • Prompts are sourced from OpenCodeReasoning and OpenCoder-Stage-2.
  • OpenCodeReasoning provides challenging coding prompts, while OpenCoder-Stage-2 covers tasks with starter code.
  • DeepSeek-R1–0528 generates 1.39M samples with an average of 17.6 responses per prompt and a maximum context length of 32,768 tokens (32K).
  • 79K unique prompts are used.

Science Reasoning Data

Prompts are sourced from S1K, Llama-Nemotron. Samples with overlapping text with test samples from science benchmarks are removed.

  • Stage-1: 226K science prompts, generating 289K samples (up to 16K tokens).
  • Stage-2 SFT: 345K samples (up to 32K tokens).
  • Stage-2 science reasoning data is upsampled by 2× before being blended into the Stage-2 SFT dataset.

Tool Calling Data

The dataset originates from Llama-Nemotron (Nathawani et al., 2025) and is designed for training models to use external tools, like function calls. On average, each conversation includes 4.4 available tools. All tool-calling data is formatted in “thinking mode.”

The dataset comprises 310K conversations with 1.41M user-assistant turns and is used in the “Stage-2 SFT training” process, with responses generated by Qwen3–235B-A22B.

Software Engineering Task

  1. Localization: The LLM identifies the relevant issue files, simplifying the original Agentless workflow by focusing solely on file-level identification. This allows the model to dedicate more resources to the repair task.
  2. Repair: The LLM generates repair edits for the localized files. To maximize contextual understanding, multiple files and surrounding code snippets are concatenated into a unified prompt. The model produces targeted, diff-style patches to preserve unrelated code structure and minimize hallucinations and syntactic errors.
  3. Patch Validation: This stage involves three phases:
  • Regression: Candidate patches are evaluated against existing regression tests to ensure compatibility and filter out those that introduce failures.
  • Reproduction: 10 reproduction tests are generated per issue instance to replicate the original bug behavior and verify functional correctness after patch application. Failing tests are discarded, and surviving tests are executed on each candidate patch.
  • Majority Voting: Results from multiple sampled generations are aggregated to select the most reliable patch. Prioritization is given to the most frequently generated patch, followed by patches with shorter generation sequences or minimal edit distances.

The training data consist of the following open-source datasets:

  • SWE-Bench-Train, the training split generated through the same pipeline as the SWE-Bench evaluation set but without human verification.
  • SWE-Fixer-Train, which consists of Python repositories with more than 100 pull requests, yielding 115K instances after applying heuristic filtering rules.
  • SWE-reBench, a public dataset containing over 21K interactive Python-based SWE tasks, constructed through a novel, automated, and scalable pipeline.
  • SWE-Smith, a synthetic dataset comprising 50K instances from 128 GitHub repositories, generated by automatically injecting bugs into codebases.

All instances originating from repositories present in the SWE-bench Verified evaluation dataset are excluded.

To construct the SFT datasets, DeepSeek-R1–0528 is employed to generate 8 responses per prompt for SWE-Bench-Train, SWE-reBench, and SWE-Smith, while producing 4 responses per prompt for the larger-scale SWE-Fixer-Train dataset. For code localization, the solution contains a prioritized list of potential buggy code file names, ranked from most to least likely to contain bugs. For code repair, the solution contains the code blocks to be replaced, and the code patch used to replace. For test code generation, the solution contains a set of unit tests and reproduction tests designed to verify both bug replication and patch correctness.

For the localization task, only samples that include all buggy code files required to address the issue (i.e., recall equals 1.0) are retained. For repair tasks, the similarity between the generated and ground-truth patches is measured using Unidiff. Instances demonstrating consistent solution quality, defined as at least 4 out of 8 sampled responses exceeding the 0.5 similarity threshold for SWE-Bench-Train, SWE-reBench, and SWE-Smith, are included in the SFT dataset. More challenging instances, defined as those with at least 1 out of 8 sampled responses achieving non-zero similarity, excluding SFT samples, are reserved for the SWE RL training. For test code generation, only the trajectories that can be successfully parsed and executed as reproduction tests without any syntax error are retained.

The resulting Code Repair dataset comprises 127K instances distributed as follows: 17K from SWE-Bench-Train, 17K from SWE-reBench, 18K from SWE-Smith, and 77K from SWE-Fixer-Train. All SWE datasets are upsampled by 3×before being incorporated into the Stage-2 SFT data blend.

SFT Results

Cascade RL

In curating the RL data, the SFT and RL datasets are strictly disjoint in terms of prompts, so the model cannot leverage memorized answers for given prompts from SFT during RL training. In Cascade RL, RLHF, Instruction-Following RL, Math RL, Code RL, and finally SWE RL are sequentially applied, progressively from more general domains towards more specialized ones.

Throughout the entire Cascade RL process, the GRPO algorithm is used. Additionally, the KL divergence term is removed entirely, which simplifies the GRPO objective to the standard REINFORCE objective with group-normalized rewards and token-level loss.

Reward Modeling

The RM is trained on 82K preference pairs from both open-source and in-house data.

  • HelpSteer2 (10K pairs) with annotations on helpfulness, correctness, coherence, complexity, and verbosity.
  • HelpSteer3 (36K pairs) spanning various domains with preference scores ranging from -3 to 3.
  • In-house data: Generated by prompting a strong LLM (DeepSeek-V3) with slightly off-topic prompts to produce “bad” responses, paired with good responses from a weaker LLM (DeepSeek-V3–0324). This strategy ensures the data is challenging for the RM.

A scalar-output RM initialised from Qwen2.5–72B-Instruct with a linear predictor on top of its last hidden layer is trained using the Bradley–Terry objective, maximizing the log-likelihood of human preferences.

Note: Qwen3 reasoning models consistently underperform Qwen2.5 instruct models when used as the backbone for reward models trained with BT loss. This is likely due to the preference data being less suitable for Qwen3’s reasoning-centric optimization.

RLHF

Introducing OOD prompts of the reward model to the RLHF stage often leads to instability or even training collapse due to inaccurate or misleading reward signals. During the RLHF stage, a subset of prompts from the reward model’s preference dataset is used. Prompts related to mathematics and competitive programming are excluded, since the reward model may not provide reward signals as reliable as those produced by rule-based or execution-based verifiers. As a result, the RLHF dataset primarily focuses on improving helpfulness, harmlessness, and alignment with human preferences, while remaining disjoint from the domains that will be enhanced in the subsequent Cascade RL stages.

For dedicated thinking models, RLHF is naturally performed in thinking mode. For unified models, RLHF training is performed in both non-thinking and thinking modes, with an equal split of prompts allocated to each mode within every batch. For reward computation for the non-thinking mode, the model answer following the assistant role is directly extracted; for the thinking mode, reasoning traces are excluded and only the final summary after the thinking process is extracted. During training, a maximum response length of 12K is used for both the 8B and 14B models in RLHF. To prevent language mixing in the generation, an additional code-switch penalty is applied when the prompt is purely in English but the generated response, including both thinking traces and summary, contains non-English tokens.

RLHF Results

Instruction-Following RL

Dataset:

  • The instruction-following dataset from Llama-Nemotron is filtered for quality.
  • 60K custom data samples are curated using user prompts from LMSYS-Chat-1M paired with instruction constraints from the IFEval taxonomy.
  • IF-RLVR training data designed to improve robustness to unseen constraint taxonomies, is also incorporated.

Training occurs in two stages, focusing on IFEval and IF-Bench-Train taxonomies respectively. Dynamic filtering is employed to stabilize training and improve results. A key challenge is mitigating the negative impact of IF-RL on human alignment capabilities acquired during the RLHF stage.

Unified Models:

  • IF-RL is applied only in the non-thinking mode of unified reasoning models to minimize interference with RLHF.
  • This approach yields substantial improvements in instruction-following capability in the thinking mode.

Thinking Models:

  • A combined reward function is used in IF-RL for dedicated thinking models, incorporating both rule-based instruction-following and human preference signals.
  • This mitigates the negative impact of IF-RL on benchmarks like ArenaHard.

IF RL Results

Math RL

Dataset:

  • AceReason-Math dataset is used.
  • 9-gram filtering prevents contamination from common benchmarks like AIME and MATH.
  • Problems unsuitable for RL training are excluded, such as multiple-choice, true/false, proof-based, multi-subquestion, non-English, and figure-referencing problems.
  • Each problem is verified by the DeepSeek-R1 model with up to eight attempts.
  • Overly simple problems solvable by AceReason-Nemotron-7B with ≥75% success rate are removed, reducing the dataset from 49K to 14K.

Math RL is initialized from RLHF-trained models, providing a stronger initial math reasoning capability compared to SFT checkpoints. This leads to improved response quality, token efficiency, and reduced training steps.

IF-RL is inserted between RLHF and Math RL to reduce model entropy and reasoning trace length. This can temporarily hurt reasoning benchmarks, but applying Math RL and Code RL with high temperature after IF-RL restores normal entropy levels.

Rewards are strictly based on answer correctness, determined by extracting the boxed answer following the <\think> token. A code-switching penalty of -1 is applied for using tokens from a different language than the prompt’s language.

A staged response length extension curriculum (24K → 32K → 40K) is used, with each stage focusing on compressing overlong reasoning, stabilizing reasoning length, and extending longer reasoning chains, respectively.

After each epoch, problems achieving 100% or 0% accuracy are filtered out. Hard problems are re-sampled with 10% probability, while easy problems are re-sampled with 1% probability to stabilize training.

Math RL Results

Code RL

The Code RL training dataset is built upon the AceReason-Nemotron coding corpus, sourced from open-source datasets like TACO, APPS, and DeepCoder.

  • Problems incompatible with standard output comparison (e.g., interactive formats) and those lacking sufficient unit test coverage are excluded.
  • Duplicates and benchmark contamination are removed using 9-gram filtering and raw problem URL matching.
  • AceReason-Nemotron-7B identifies trivial problems (solved in all 8 rollouts), and DeepSeek-R1–0528 filters out intractable ones (unsolved in all 8 rollouts). This results in a final training set of 9.8K samples.

Code RL training follows Math RL, which acts as a warm-up, stabilizing training and enhancing reasoning capabilities. It is a single-stage training where maximum response length is set between 44K–48K tokens.

  • A reward of 1 is given only if the generated code passes all test cases; otherwise, 0.
  • A reward of 0 is assigned if tokens from a language different from the prompt’s language are detected in the reasoning trace.

SWE RL

  1. Ground-truth only: Similar to SFT, prompts are constructed using only the ground-truth localization files.
  2. Mixed localization: Augmented prompts are built using both the files localized by DeepSeek-R1–0528 and the ground-truth localization files. Up to five files are included in total and all ground-truth files are present. The initial prompt contains only the ground-truth files. Noisy files are then added one by one until the total prompt length would exceed 𝑙; if the limit is exceeded before adding any noisy files, the instance is discarded. To enhance robustness, the order of files within each prompt is randomized.
