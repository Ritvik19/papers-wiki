Papers Explained 587: OpenThoughts Agent

The OpenThoughts-Agent (OT-Agent) project provides a fully open data curation pipeline for training agentic language models, systematically investigating the effects of task sources and diversity through over 100 controlled ablation experiments. . Leveraging these insights, OT-Agent compiles a 100K example training set and fine-tunes Qwen3–32B, achieving an average accuracy of 44.8% across seven agentic benchmarks, a 3.9 percentage point improvement over the previous best open-data model, while demonstrating superior scaling properties.

The dataset is available at HuggingFace.

SFT Data Pipeline
OpenThoughts-Agent Full Data Pipeline.
The best dataset is the one that produces the highest-performing agent on downstream benchmarks. To do so, each pipeline step is ablated independently, and the best-performing strategy is selected based on the average z-score across three benchmarks. The z-score of every candidate strategy’s accuracy is computed across the stage’s full candidate set (subtracting the stage’s per-benchmark mean and dividing by its standard deviation), then the three resulting per-benchmark z-scores are averaged.

For each ablation experiment, the full pipeline is utilized to generate 10,000 trajectories for each data strategy, and Qwen3–8B is finetuned on each dataset using full-parameter SFT, learning rate 4e−5 with cosine schedule, global batch size 96, 7 epochs, and 32,768 context length.

Unless otherwise specified, trajectories are generated by GLM-4.7-AWQ acting as the teacher in the terminus-2 harness inside Daytona sandboxes.

The core suite consists of three benchmarks:

OpenThoughts-TBLite (100 tasks), a curated collection of 100 Terminal-Bench style tasks balanced across four difficulty buckets and engineered as a fast proxy for the full Terminal-Bench 2.0 performance
SWE-Bench Verified-100 (100 tasks), a stratified subsample (by repository) of the 500-task human-validated SWE-Bench Verified split, where an agent produces a patch against a Python repo at a fixed commit, binary-scored by the upstream test harness
Terminal Bench 2 (89 tasks), hand-crafted, human-verified tasks that span SWE, biology, security, system administration, and machine learning.

All evaluations run inside isolated Daytona sandboxes using the terminus-2 agent harness, with n = 3 stochastic re-runs per task and standard error reported across trials. To measure generalization, pipeline experiments exclude a held-out set of out-of-distribution benchmarks, which are only measured once pipeline experimentation is complete. This held-out set consists of Aider Polyglot, BFCL, MedAgentBench, GAIA, and FinanceAgent-Terminal.

Sourcing Tasks
Full task generation strategy ranking.
To efficiently find the best task data generation strategies, a set of 95 task generation strategies covering different initial sources, modes of generation (synthetic vs. not synthetic), and knowledge domains for those tasks is ablated. The top-performing task generation strategies include synthetic issue-resolution tasks such as SWE-Smith and IssueTasks datasets, human-written computer-use questions such as StackExchange SuperUser and Tezos, and other strategies.

Mixing Tasks

The use of the top 1, top 2, and so on datasets in the mix is simply ablated. For the Top-N mixing strategy, the top N data generation strategies are taken, and 10,000/N task descriptions are sampled from each.
Mixing top-ranked task generation strategies, random shuffle within task.
Mixing around the Top 4 or Top 8 task generation strategies works best.

Task Augmentation Strategies

Different methods for augmenting task descriptions are explored, such as using an LLM to combine tasks from different sources, add new constraints to each task, harden the task descriptions, and more.
Task description augmentation strategies are within noise.
All interventions fail to improve the baseline of leaving the task description untouched after generation.

Filtering Tasks

After determining the final mix of task generation strategies, filtering out poor tasks from a set of task descriptions can improve downstream performance. The ablation of the set of task description filters from OpenThoughts is repeated.
Filtering task descriptions with LLM-based difficulty signals improves performance.
Similar results are observed: LLM task description filters yield the largest improvement among the filters tested. Filtering tasks to those that GPT-5 requires more tokens to solve finds tasks that lead to roughly 3 percentage points improvement across all benchmarks.

Teacher Model Prior work has shown that the choice of teacher can make a significant difference in downstream evals. Building on this awareness, the best mix of task descriptions is taken to generate a dataset with different teachers that perform well on TerminalBench 2.0, including GPT-5.3-Codex, Kimi K2.5, GLM-4.6-AWQ, GLM 5, and the baseline GLM-4.7-AWQ.
Teacher model ablation: stronger model ̸= better teacher.
Despite GPT-5.3-Codex being the best-performing model, it is a worse teacher than GLM-4.7-AWQ, representing a roughly 5% decrease in performance on TerminalBench 2.0. The best teacher is GLM 4.7, despite being older and less performant (e.g., on TerminalBench) than Kimi K2.5.

Filtering Agent Rollouts Simple heuristic filters are applied, including removing traces that hit a timeout during generation, removing subagent traces, and removing traces with fewer than 5 turns.
Filtering agent rollouts: keeping longer trajectories helps.
Methods that yield longer agentic traces yield better performance, with filtering traces with fewer than 5 turns yielding the largest improvement in downstream evaluation scores.

Scaling Up SFT Data

After the pipeline ablations, the final pipeline yields a dataset of 10K datapoints. To increase the dataset size, several simple strategies are possible:

Using the same task descriptions and generating more agentic rollouts per task.
Using more task descriptions from the original sources
Using synthetic augmentation to create new task descriptions
Using more initial sources. Method 1 is chosen since it is the simplest.

Performance plateaus from 31.6K to 100K (+3pp on SWE-Bench Verified-100, −2pp on Terminal-Bench 2.0; both within standard error), suggesting that task-description diversity is the bottleneck. While Method 2 would be a simple fix, there is a limitation due to the initial sources; for example, Tezos contains only 997 unique task descriptions.

Sourcing from more tasks from Top-4, Top-8, and Top-16 datasets at the 100K scale is attempted. Adding more sources beyond Top-4 does not reliably help: Top-8 does not significantly outperform Top-4 on every benchmark, while broadening to Top-16 hurts on every benchmark.

Synthetic task augmentation is then used. Concretely, the four highest-scoring sources (swe-smith, stackexchange-superuser, stackexchange-tezos, and issue-tasks) are used, and the Tezos subset is replaced with a synthetically augmented version of itself. Instruction-rewriting strategies are applied to those same 997 base problems, expanding their distinct surface forms from ∼902 to over 21K without introducing any new underlying problems. The gpt-5-nano response-length signal is then used as upsampling weights rather than as a hard top-k filter , every unique task receives at least one rollout, with the remaining capacity allocated proportionally to score.

The ≥ 5-turn trace filter is then applied uniformly across all four sources. Continued performance gains are seen at larger dataset scales.

Reinforcement Learning

Many high-profile RL datasets, including SWE-Smith and R2EGym, followed a similar approach: select a representative GitHub repository whose state and dependencies can be captured in a Docker container, select or synthesize a flawed commit with failing tests, and generate a natural-language problem statement describing the issue and requesting the agent turn the failing tests green. These efforts are incorporated into a larger-scale and more systematic series of ablation studies in order to investigate to what extent model performance depends on the source of the RL training data.

To control compute consumption, focus is placed on RL investigations in the 8B regime using a distilled checkpoint (OT-Agent-ColdSFT) trained on SWE-Smith traces generated by a GLM 4.7 AWQ teacher with thinking. Async RL is run using the RLOO algorithm with standard binary rewards on verifier success.

Six sources are compared spanning competitive programming recast as Python contracts (pymethods2test), real-repository bug-fixing (inferredbugs), competitive-programming environments (code-contests), an LLM-filtered Nemotron code-oracle mix (nemotron-code-oracle), an LLM-verified freelancer-task set (llm-verifier-freelancer), and natural-language-to-Bash tasks (nl2bash), as well as SWE-Smith and R2EGym, with the same evaluation conditions as SFT dataset.
Data source strongly influences agentic RL performance.
The strongest source, pymethods2test, is a mix of Codeforces / CodeChef / TopCoder style competitive-programming problems that have been re-cast as single-function Python contracts with synthesized docstring-style task descriptions and auto-generated unittest suites. There is no multi-file editing, no repository navigation, no shell-state accumulation across turns. Skills exercised include 1D/2D dynamic programming, string and pattern matching (KMP), combinatorics, matrix/grid construction, ad-hoc puzzles, and formatted table/string generation. Reference solutions average around 20 LOC and task description around 200 words. This dataset is highly reproducible (no potentially stale github references), highly usable (all tasks use the same build environment) and has a clear, and in this case appropriately moderate, difficulty ceiling. The concise but challenging source tasks induce the cold-start model to adopt a consistent problem-solving pattern; during RL, it replaces loops of thinking and exploratory (sed and grep) tool calls with a compact explore, patch, and submit policy.

Among the alternatives, the synthetic-and-competitive-programming sources (inferredbugs, code-contests) lead on ID, while the more heterogeneous tool-use sources (llm-verifier-freelancer, nl2bash) are competitive on OOD despite weaker ID scores. The moderate ID / OOD decoupling suggests that data sources emphasizing single-function code correctness transfer most cleanly to the SWE/terminal Core benchmarks, while broader tool-use data buys OOD generalization at some ID cost; only pymethods2test sits at the top of both.
RL main results (8B scale).
The complete post-training pipeline (SFT + RL) outperforms the baselines on both core benchmarks, as well as on average across the entire benchmark suit
RL on top of moderately strong SFT outperforms other strategies.
Undertrained SFT models benefit more from RL, and ultimately outperform pure-distilled models and RL-only models.
