Papers Explained: EMO

LLMs are usually deployed as monolithic systems, requiring the entire model even for tasks needing only specific capabilities. MoEs theoretically allow only parts of the model (experts) to be used as needed, but in practice, restricting inference to expert subsets harms performance due to low-level lexical specialization. EMO is a new MoE design that enforces modularity by having tokens within a document share a pool of experts without needing human-defined domains which leads to coherent, domain-level expert specialization.

EMO

The goal of EMO is to pre-train an MoE with modularity as the first-class objective, i.e., expert subsets should be usable in isolation for a particular downstream domain, and the full model remains a strong general-purpose model.

A straightforward approach to develop modularity is to enforce expert specialization in MoEs by routing tokens to experts based on predefined semantic domains (e.g., math, biology, code).

However, this formulation requires domain labels across pretraining data, which can be ambiguous, difficult to obtain, and injects human biases. Having fixed domains also restricts flexibility, making it difficult for the model to be applied to new domains during inference.

Instead, modular structure is induced without explicit domain labels. The key observation is that tokens within the same document usually come from the same domain. Therefore, document boundaries are treated as a weak supervisory signal: for each document, the router selects a shared expert pool, and all tokens in that document choose their active experts only from this pool. Different documents can use different pools, allowing modular expert subsets to emerge directly from the training data.

EMO Formulation

The goal of EMO is to induce modularity by leveraging document boundaries as a weak supervisory signal. EMO achieves this by selecting a document expert pool for each document and constrains all tokens in the document to route within this pool during training.

Consideration 1: Load Balancing: A central challenge is that load balancing and document-level routing appear to impose opposing pressures. This conflict arises under standard micro-batch load balancing, where the load-balancing loss is computed over only a few documents. This is addressed by adopting global load balancing, aggregating routing statistics across data-parallel groups.

Consideration 2: Choosing Expert Pool Size: Fixing a single expert pool size d works well during training but limits inference-time flexibility. The model “overfits” only to expert sets of size d and performs poorly when deployed as expert subsets that aren’t of size d. To enable the model to support expert subsets of all sizes, d is treated as a random variable and sampled independently for each document during pretraining.

Experimental Setup

An MoE with 1B active and 14B total parameters, consisting of n = 128 experts (nr = 127 routed, ns = 1 shared), with k = 8 experts activated per token, is considered. The baseline MoE and EMO are trained from scratch on 1 trillion tokens from the OLMoE pretraining corpus followed by an additional 50B-token linear annealing phase. For ablations, models are additionally trained on 130B tokens and include comparison to dense baselines and smaller MoEs. The architecture largely follows that of OLMoE, with several key improvements: (1) adding a shared expert, (2) using pre-norm instead of post-norm, and (3) removing QK-norm.

The evaluation of the models is conducted under two settings:

Full-model Evaluation: reflects deploying the entire pretrained model for a broad set of tasks. Evaluation is done in zero-shot mode across five suites:

  • MC9: Average over nine multiple-choice benchmarks (ARC-Easy, ARC-Challenge, BoolQ, CSQA, HellaSwag, OpenBookQA, PIQA, SocialIQa, and WinoGrande).
  • Gen5: Average over five generative benchmarks (CoQA, SQuAD, Natural Questions, TriviaQA, DROP).
  • MMLU
  • MMLU-Pro
  • GSM8K

**Selective Expert Use: ** only a task- or domain-specific subset of experts is activated. Evaluation is conducted on coarse-grained domain groupings from MMLU and MMLU-Pro (math, physics, health, philosophy, history, with 161 and 131 domains respectively), as well as GSM8K. For each domain, a small validation set (as small as a single few-shot example) is used to select relevant experts. Two selection methods are tested:

  • Simple Aggregation Method: Aggregates routing probabilities across tokens and ranks experts by average routing probability.
  • Easy-EP: A computationally expensive but state-of-the-art selection approach.

Top-d experts in each layer are chosen based on selection, while the rest are discarded, resulting in a domain-specific model.

Evaluation

Full-Model Evaluation

  • The baseline MoE is competitive, outperforming OLMOE, trained on 5T tokens despite using only 1T tokens.
  • EMO matches the performance of this standard MoE.

Selective Expert Use

  • Standard MoEs Degrade Sharply: When restricting to expert subsets, standard MoEs suffer significant performance drops (e.g., over 10% loss when retaining 25% of experts), even with advanced selection like Easy-EP. Performance can fall below that of a dense model with matched parameters.
  • EMO Enables Modular Use: EMO retains near full-model performance even when using small expert subsets (e.g., only a 1% drop with 25% subsets and 3% with 12.5%). Subsets with as few as 12.5% experts can still perfectly recover full performance on tasks like GSM8K.
