# Agent Harness

#concept

An **agent harness** is the product and infrastructure layer that wraps a language model into a working agent. It owns the system prompt, the tool descriptions and tool implementations, the context-window strategy, the orchestration of subagents and model switches, the observability and error-handling layer, and the experimentation harness used to evaluate changes. The harness is what turns a raw model into a usable coding agent, and the [[Continually Improving Our Agent Harness]] article from Cursor is the corpus's clearest statement of how a serious harness is built and maintained.

## What A Harness Owns

A harness sits between the user and the underlying model. Its responsibilities, drawn from [[Continually Improving Our Agent Harness]] and reinforced by [[Papers Explained - Composer 2]] and [[Introducing Composer 2.5]], typically include:

- **Context-window construction.** What static context (operating system, git status, current and recently viewed files) ships up front, what tool descriptions are exposed, what dynamic affordances the model can call to pull in past conversations, terminal sessions, or codebase slices.
- **Tool definition and execution.** The exact tool surface a model sees, with formats picked to match the model's training distribution. Cursor explicitly notes that OpenAI models get patch-style edits because that is what they were trained on, while Anthropic models get string replacement.
- **Prompting per model and version.** Different models, and different versions of the same model, get different system prompts and tool prompts. Quirks like "context anxiety" — refusal behaviors that emerge as context fills — are mitigated at the harness layer rather than waiting for the next model release.
- **Mid-conversation transitions.** Switching models mid-chat means swapping in a different harness variant on a transcript that was generated by another model; the harness handles takeover instructions and either accepts a cache miss or summarizes the transcript. [[Cursor Router]] automates this decision: a classifier routes each request to the best model, with cache-aware training that accounts for routing-induced cache misses.
- **Model routing.** [[Cursor Router]] classifies each request on query, context, task complexity, and domain, then routes to the most effective model in the pool — extending per-model harness customization from a manual user choice to an automated, data-driven system.
- **Dynamic tool loading.** [[Dynamic Tool Calling]] defers loading native tool descriptions until first use, mirroring the MCP lookup pattern and keeping common tools like read and edit hot in the prompt.
- **Subagents and orchestration.** Spawning a subagent with a fresh context window is itself a harness affordance, and multi-agent orchestration (planning, fast edits, debugging) is described as fundamentally a harness problem.
- **Observability and error classification.** Bucketing tool-call failures (for example, `InvalidArguments`, `UnexpectedEnvironment`, `ProviderError`, `UserAborted`, `Timeout`), maintaining per-tool and per-model baselines, and alerting on anomalies and unknown errors.
- **Experimentation surface.** Running A/B tests across harness variants in production, paired with offline evals such as [[CursorBench]] and quality signals such as [[Keep Rate]] and LLM-judged user-response semantics.

## How Harnesses Evolve

Cursor's history is a useful reference arc. In late 2024, models were poor at choosing context, so the harness shipped heavy static context (folder layout, semantically retrieved snippets, compressed user attachments) and aggressive guardrails (rewriting too-short file reads, capping per-turn tool calls, surfacing lint and type errors after every edit). As models got better at picking their own context, those guardrails were removed and replaced with [[Dynamic Context]] retrieval initiated by the agent itself.

More generally, harness evolution tends to follow a pattern of **knocking down guardrails as model capability rises** while **adding new affordances** the model can use: more dynamic-context surfaces, more tools, richer subagent shapes. The balance is constantly retuned; what was a useful guardrail in one model regime becomes overhead in the next. This is why the post argues that harness engineering becomes more critical, not less, as models improve.

## Why Harness Work Matters

The harness determines whether a strong model becomes a strong agent. The same model in a harness fitted to its quirks runs measurably faster, smarter, and more efficiently than the same model in a generic harness — Cursor's early-access launch process explicitly leans on this for weeks before shipping.

The corpus offers two empirical anchors:

- [[Composer: Building a fast frontier model with RL]] states that Composer (1) RL training uses the same production [[Agent Harness]] tools (edit, semantic search, grep, terminal) and unifies RL sandboxes with deployment by adapting Background Agents VM scheduling—hundreds of thousands of concurrent coding environments at training scale.
- [[Papers Explained - Composer 2]] reports that Composer 2 is trained with reinforcement learning **inside the same Cursor harness used in production**, so the model and harness co-evolve. CursorBench-3 accuracy improves from 38.0% (Composer 1) to 44.2% (Composer 1.5) to 61.3% (Composer 2), and the Composer 2 page treats the harness as part of what is being trained against, not a fixed wrapper.
- [[Introducing Composer 1.5]] trains **[[Self-Summarization]]** inside RL so agents can continue long tasks when context fills—behavior that later Composer generations inherit at the model level rather than only via harness transcript compression.
- [[Papers Explained: Is Grep All You Need]] shows the same principle for retrieval: the relative performance of grep and vector search changes across Chronos, Claude Code, Codex, and Gemini CLI, and even changes when results are delivered inline versus through files.
- [[Papers Explained 547 - Terminal-Bench]] explicitly reports terminal-task performance "by model with its best agent harness," which is direct evidence that benchmark scores are entangled with harness choice and that comparing models without controlling for harness is misleading.

Beyond raw scores, the harness is also where degradations are caught. Tool errors compound through [[Context Rot]] — a failed tool call sits in context, wastes tokens, and biases later decisions — so per-tool, per-model error baselines and anomaly alerts are central to keeping a deployed agent stable as it scales.

## Common Failure Modes

- **Out-of-distribution tool formats.** Forcing a model to use a tool format it was not trained on costs reasoning tokens and increases mistakes.
- **Static context bloat.** Shipping too much static context up front leaves less room for dynamic retrieval and erodes performance through length-related degradation, as documented in [[Papers Explained 445 - Context Rot]].
- **Cache penalties on switch.** Mid-chat model switches are guaranteed cache misses and can be slow and expensive on the first turn.
- **Summarization detail loss.** Compressing transcripts at switch time can drop the very details that mattered for a complex task.
- **Cross-model tool-call drift.** A model that took over mid-chat can be tempted to call tools that appear earlier in history but are not in its own tool set; explicit takeover instructions help.
- **Context anxiety.** As context fills, some models start refusing work and hedging task scope; this is mitigated with prompt adjustments rather than left to the model.

## Mitigations And Patterns

- **Match tool formats to training data** for each model and version.
- **Prefer dynamic context** the model can request, and keep the static base small.
- **A/B test harness changes** alongside offline benchmarks; rely on outcome signals like [[Keep Rate]] and user-response classification rather than only operational metrics.
- **Classify and baseline tool errors per-tool and per-model**, and alert when error rates exceed those baselines.
- **Use subagents with fresh context windows** to avoid the costs of mid-chat model switches when behavior really needs to change.
- **Treat early-access access to new models as harness work**, not just model-evaluation work.

## Coding Harness Specialization

[[Components of A Coding Agent]] by [[Sebastian Raschka]] treats a **coding harness** as the software-engineering specialization of an agent harness: live repo context, stable prompt-prefix caching, structured tools with validation and approval, context clipping and transcript compression, dual-layer session memory (full transcript vs working memory), and bounded subagent delegation. The article's [[Mini Coding Agent]] reference implementation complements production-focused sources like [[Continually Improving Our Agent Harness]] with a from-scratch pedagogical taxonomy. See also [[Coding Harness]].
